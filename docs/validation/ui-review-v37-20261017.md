# v37: 설치기 초기 검사 중단 후 재검사 복구

상태: done-scoped / 새 설치기 사용자 확인 대기. 설치기 수정 범위이며 앱 자동 업데이트나 전체 P0 완료가 아니다.

## 원인과 사용자 동작

초기 위치 검사는 현재 설치와 일치하는 기록 generation을 탐색하고 새 설치 가능 여부를 판단한다. 기존 다시 검증 명령은 이 탐색을 거치지 않고 현재 입력/기본 기록 경로로 직접 기존 설치를 검사했다. 초기 검사를 취소하면 미확정 경로를 검증해 NotFound/InvalidData가 되거나 Unknown 상태에서 설치가 계속 비활성화될 수 있었다. 중단이 파일을 삭제한 것으로 단정하지 않는다.

packaged 모드의 다시 검증은 기존 worker ACK 뒤 위치·현재 기록을 재탐색한다. 빈 설치 위치는 설치 가능 상태로 돌아가며 기존 설치는 유일하게 일치하는 기록의 실제 검사 결과만 실행 준비에 반영한다. 명시 네 경로 모드의 직접 검증과 실행·제거의 fresh guard는 유지한다. 늦은 취소 결과·입력 revision이 다른 결과·모호한 기록은 실행 권한을 만들지 않는다.

검사 취소 worker가 종료하면 중단 완료와 다시 검증 행동을 안내한다. 취소 버튼은 검사 중단/설치 중단/제거 중단/실행 취소로 실제 작업을 구분한다. 설치 중단은 자동 원상복구가 아니며 만들어진 파일과 기록은 보존된다.

## 검증

실제 Windows private desktop의 native State·EDIT·버튼과 production queue/stop/recheck/poll 경로를 사용하는 회귀를 먼저 실행했다. 초기 검사 취소→다시 검증 뒤 Unknown이 남는 RED(exit101, 0 PASS/1 FAIL)를 보존했다. 수정 후 GREEN v1과 취소 ACK 전 중복 요청 차단·반복 재검사를 추가한 GREEN v2가 각각 1 PASS/0 FAIL로 통과했다. 과거 기록·sentinel은 같은 bytes를 유지했고 빈 target은 생성되지 않았다. 이 시험은 전체 설치된 bundle의 실행 준비 성공을 대신하지 않는다.

Windows whole37 fmt·strict clippy·workspace test·release는 실제 모두0, **1685 PASS/0 FAIL/43 ignored/43 harness**다. 새 ignored 회귀는 별도로 명시 실행해 실제 통과했다. source675와 v36 대비 정확 두 파일 변경, Cargo.lock 유지, CPU/CLI byte-identical을 Root가 대조했다.

실제 packaged 설치기에서도 원35 payload와 명시 원36/새37 설치기를 각각 고정한 혼합 합성 fixture로 install→remove→samepath reinstall→cold 검사 중202취소→ACK→203을 실행했다. 원36은 현재 suffix-1 대신 base 기록을 검증해 InvalidData/SOURCE_CHANGED·실행 비활성으로 실패했고, 새37은 suffix-1을 재발견해 실행 준비/기본212·앱 실행 활성으로 복귀했다. 양쪽 최초 시도에서 검사 중단을 포착했다. 기존/새 기록 각5개와 payload5개 원 bytes·hash·sentinel을 보존하고 각 설치기2개 자연0·Job0·private/input desktop 복구를 확인했다. CPU 실행은 요청하지 않았다. **새37 payload 전체 runtime 인수로 확대하지 않는다.** Root는 실제 원 로그·pins·상태를 재검토하고 baseline 오류/green 중단 안내/green 실행 준비 PNG3장을 직접 확인했다.
